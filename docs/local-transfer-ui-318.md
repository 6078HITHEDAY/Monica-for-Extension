# Local transfer and encrypted attachments — 2026-10-11

This block exposes the transaction from `010927e` through the production extension runtime and manager. It does not complete Android parity or add KeePass/Bitwarden destinations.

## Behavior

- The shared transfer dialog accepts the local vault or an unlocked MDBX target. The local-vault source card provides an entry even when no external vault exists. Existing Passkey/Steam entries preserve the filtered candidate scope. Local folder identities come from a manager-only endpoint; they are not presented as Native collections.
- Previews expand dependencies and reject complete failing groups. Authenticated source readers preserve file names, bytes and source-scoped folder identities. Missing folder names are not treated as root. A changed form discards its pending preview; execution requires the original request. Local move confirmation remains mandatory, and foreign-source moves remain blocked pending durable deletion.
- Files, items, original source records and recovery receipts are saved in the same encrypted envelope. Copy preserves credential keys/IDs/counters/flags and rich fields under the existing transaction policy. No remote deletion is performed by this local copy.
- Local files use the existing attachment dialog, including previews on wallet/card components. Replacement/deletion require the current metadata revision. Successful operation receipts survive restart; later file deletion is not undone by replaying the original copy/upload. Download handles validate the unlock session and file revision on each chunk; locks clear caches and invalidate in-flight preparation.
- Limits: 200 related items, 512 files per item, 16 MiB aggregate attachment plaintext per selected transfer and per local item. Four cached plans and four download handles expire after five minutes. The concurrent-start limit is checked after awaited work as well. Existing encrypted-envelope size limits still apply.
