# MDBX → Bitwarden move recovery

The batch transfer dialog now supports moving eligible MDBX sources into Bitwarden. It preserves the verified source conversion used by copying: rich password fields, complete password projects, supported SSO relationships, portable Passkeys, supported password history and attachments. Unsupported content or unresolved relationships keep the whole dependent component at the source. Native commit history remains in the source vault and the preview explicitly says so; this is not a conversion of the full native timeline.

## Transaction boundaries

- Version 3 encrypted batch records retain the original indexed sources, authenticated vault identity, resource fingerprints, whole-vault deletion revision and native commit receipts. Existing version 1 copies and version 2 local moves keep their previous semantics.
- All target Ciphers and attachments must be saved and authenticated before source deletion. Native relationship scans also detect members and incoming owners absent from the extension index. Copy previews keep the inexpensive identity catalog; moves add sanitized relationship metadata without retaining decrypted native secrets.
- Independent complete components in the same provider are packed into native transactions of at most 50 objects. A component exceeding that limit is blocked rather than split. The overall selection limit remains 200.
- The deletion revision is captured before rereading native content, files and membership, then checked again. It is durably saved before the native call and never silently refreshed. A later attachment-only change can therefore stop deletion even when Object heads still match.
- Source and target provider queues are reserved together, with the selected provider set rechecked after waiting. Pending native moves block ordinary source sync, direct native edits, attachments, history/snapshot mutations and competing source moves. Indexed sources and dependency membership are pinned from deletion authorization through final adoption; connection removal, disabling and rebinding are blocked throughout pending native moves.
- Native deletion runs under the encrypted-vault mutation lock using detached arguments. If a reply, receipt write or final adoption fails, restart reuses the same intent or commit receipt. Deleted sources are not read again. Final adoption still requires a fresh authenticated target readback and every native receipt, then removes the old indexed items, source envelopes and local ownership metadata in the same encrypted write that marks the batch complete.
- Reopening the same MDBX working copy may update helper verification timestamps, display/default settings and diagnostics. Version 3 source hashes exclude those incidental values while retaining connection bindings; the journal separately checks the native vault ID. Credential IDs, private keys and intentionally zero counters are not rewritten.

## Validation

Unit validation covers 3,384 distinct tests in 286 files. The full run passed 3,379/3,380; the new 51-item encrypted recovery test exceeded its 20-second test budget under concurrent suite load. That test received a specific 60-second budget, without changing assertions, and all 66 tests in the affected coordinator, native membership and direct-write files passed afterward. Those include four additional tests for oversized components and unindexed Passkey bindings. No other full-suite failure occurred. Production build, project/interop checks, strict test type checks and the security audit of 217 runtime commands passed.

The new coordinator tests exercise lost native replies, failed encrypted receipt writes, failed final adoption, locking during deletion, source/dependency/connection pins, queued-provider changes, reopen metadata, target readback rejection and partial native transaction completion. A 51-item transfer uses 50+1 native groups and resumes only the unfinished group with exactly 51 target Ciphers. Oversized connected components remain whole and blocked.

Installed Edge 155.0.4283.45 passed three scenarios on the final production build: local → Bitwarden move, MDBX → Bitwarden copy, and MDBX → Bitwarden move. The native move creates a real browser Passkey plus a two-password project and attachment. It survives the lost first Cipher reply, explicitly reopens the native working copy after a full browser restart, confirms ordinary sync/direct deletion are blocked, then survives a sustained target readback outage after native source deletion and another full restart. Authenticated native deleted-object listings prove source deletion; exactly three Ciphers exist. A fresh independent client preserves the original credential/private-key bytes and zero counter, verifies a WebAuthn assertion against the original registration public key, and reads the original attachment bytes. Both normal and 375px-wide confirmation layouts were inspected. Temporary Native Messaging registration was restored.

Final local artifacts: `.artifacts/bitwarden-mdbx-move-edge-delivery-20261012` contains the passing local move and MDBX copy, while `.artifacts/bitwarden-mdbx-move-edge-complete-20261012` contains the passing native move. Each passing case saves `acceptance.json`. The last native move's three-item preview took 1,022 ms; scripted registration including the confirmation interaction took 6,178 ms. These are scenario measurements, not a large-vault performance benchmark. One intervening final-build run timed out waiting five seconds for the fresh-client Passkey chooser; the unchanged chooser assertion passed on the subsequent completed run. Its timing variability remains a follow-up.

The initial installed Edge run found that reopening a native vault changed the helper verification timestamp included in the source hash. This has been fixed and covered by restart regressions. A second failure came from a synthetic probe attempting to disclose tombstoned objects; it now checks the authenticated deleted-object listing. The simulated post-deletion outage must remain active through Bitwarden HTTP retries; a single 503 was transparently retried and did not interrupt the move. Native registration, preview and the initial verified execution/outage UI also outlived the default five-second wait. Those native operations now have an explicit 20-second test budget, with registration and preview recording elapsed time; exact outcome and data assertions remain. The cause of the timing variability is unproven. All failure evidence remains local.

Local evidence uses `.artifacts/bitwarden-mdbx-move-*20261012*`. The editable design and local Canvas link are saved in `docs/design/bitwarden-mdbx-move-319.m3e.json` and `docs/design/bitwarden-mdbx-move-319.md`; design files and screenshots are not included in the commit.

## Remaining scope

This block covers eligible MDBX → Bitwarden moves. Other remote-source moves, full native timeline conversion, unresolved note/OTP/Passkey association mappings and explicit keep-both resolution after a source edit remain open. Current Android/F-Droid/system Credential Manager, live OneDrive and nearby transport/per-recipient consent acceptance remain separate work. Tests use synthetic data and isolated installed Edge profiles, not user accounts or Chrome. No Android source/build/device operations or release publication are included.
