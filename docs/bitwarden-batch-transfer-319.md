# Bitwarden batch destinations — 0.1.37 development

## Scope

The manager can now copy into an authenticated personal Bitwarden/Vaultwarden vault, select its native folders, and resume a persisted batch after browser interruption. The same dialog is available from the Bitwarden source card, local source card, and Passkey/Steam selection entry points. Moves into Bitwarden remain disabled because durable source deletion is not implemented.

Native Bitwarden sources retain the full Cipher, including password history, unknown native values, OTP and all FIDO2 siblings. Fixed-point selection expands native siblings, password projects and SSO dependencies; if one member cannot be preserved, the whole connected component is blocked. Copies use a new shared project identity and resolve SSO references to confirmed destination server IDs. Numeric-only Room references and unsupported note/OTP relationships are refused. Local entries undergo a codec round trip and explicit field comparison, including custom-field protection/type and binary credential identity. Other backends and archived native origins currently stop with an explanation instead of silently discarding unprojected data.

## Persistence and recovery

- The entire reviewed batch, source fingerprints, encrypted Cipher preparations and attachment bytes are staged in one encrypted vault transaction before any remote write. Selection is limited to 200 items and attachments to 16 MiB per batch. Four private previews expire after five minutes and are cleared on lock.
- A new folder has a persisted randomized encrypted name and an attempt record before POST. A full authenticated scan must find exactly that ciphertext once. A matching plaintext name, missing result, duplicate identity, rename or deletion never authorizes another create. Existing folders retain their selected IDs and encrypted names. An application create is attempted once; browser-level transport replay can still produce an ambiguous result, which stops recovery.
- All folders must be confirmed before Ciphers can execute. Prepared templates cannot execute until folder and SSO bindings are durably materialized. Dependencies are verified before their dependants, and materialization is not repeated with new ciphertext or a new identity.
- Each Cipher and each attachment retain their own durable receipts. Recovery downloads and validates files before completion. Ordinary sync refuses to adopt partial batches. A final read-only provider sync checks native revisions, Cipher proofs, file sets, SSO routing and every sibling before atomically saving the complete projection and completion result.
- Atomic adoption refers to the extension's encrypted local index. Bitwarden's per-Cipher API is not a remote batch transaction; another client may observe the already-created subset while a transfer is interrupted. Recovery preserves those copies and finishes the saved graph instead of deleting or duplicating them.
- Completed replay performs no remote calls and does not replace later edits. Cancellation is allowed only while no folder or Cipher has an attempted write. Original sources and original Passkey credential/private-key bytes are preserved; zero and positive counters are not normalized.
- Execution handles bind to an unlock session and the original provider binding. Token-only compare-and-swap preserves newer refresh results and unrelated account settings. Final adoption applies fresh server metadata only where the account setting still matches its pre-sync value, preserving concurrent preferences as well as tokens. New batch snapshot hashes exclude rotating Bitwarden tokens; existing standalone receipt hashes keep their original meaning.
- New recovery commands are manager-only. Public pending results contain the request and reviewed plan, not Cipher payloads, attachment bytes or account keys.
