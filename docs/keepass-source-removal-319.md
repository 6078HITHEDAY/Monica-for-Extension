# KeePass source removal file transaction — 2026-10-12

This block provides the internal file and persistence primitive needed for cross-provider moves from KeePass. **It does not enable new cross-provider move actions.** KeePass-to-Bitwarden remains copy-only until destination verification, encrypted authorization, provider queues, cloud publication and source-index adoption are integrated together.

## Implemented boundary

- A versioned request binds the original operation UUID, destination identity/proof, source account identity, exact encrypted working-file digest, whole native content digest and selected source snapshots. Request hashing includes the file/remote location and OneDrive connection identity. Tokens and passwords are not part of the operation identity.
- The initial write requires the matching live KeePass session and source mode. Every source must still match its acknowledged item fingerprint; the native content hash additionally covers fields, protection, metadata, history, attachments, groups and deleted objects. A changed file, an unsaved source change, a locked/replaced session or a changed storage revision stops the operation.
- Native-tree checks reject duplicate entry/group UUIDs and additional root groups before relying on the indexed catalog. Complete projected password projects and supported SSO links are required. Native field references use the existing UUID/name resolver; references crossing the selection boundary, malformed/unresolved references, hidden or malformed project metadata and unresolved numeric links prevent removal. Native Monica payload containers are checked for binding fields that the reader can omit. This is not a general parser for arbitrary third-party plugin relationships.
- The operation soft-deletes whole entries to the KDBX recycle bin in a disposable database. Original UUIDs, credential IDs, private-key bytes, zero or positive signing counters, protected/unknown fields, history and binary content remain in the source file. Disabled/missing recycle-bin metadata is repaired; a root group incorrectly configured as the bin is refused.
- The output is saved, independently loaded, and compared against the full expected native content digest. Selected entries must appear in the native recycle bin. No source index or live database is changed by preparation.
- Local-file, WebDAV and OneDrive working-copy services atomically persist the complete encrypted KDBX and an AES-GCM encrypted `transfer-source-remove` receipt using the storage revision precondition. The receipt contains only input/output hashes, source/native IDs and the recycle-bin UUID; no snapshots or private keys.
- Restart recovery validates the original request and returns the committed receipt without another removal or a live session. A later user restoration or file edit is not overwritten. A changed destination/proof is a different request and cannot consume the old receipt. Existing expired-receipt markers continue to prevent repeating retired operations.

## Required caller contract

The destination proof is a binding value, not independently authenticated by this file primitive. A trusted coordinator must verify all destination records and attachments, then durably save this exact source-deletion authorization in the encrypted vault journal **before** calling it. No runtime message exposes the primitive.

The coordinator must serialize source/target provider operations throughout prepare, persist, publish and adoption. The final session guard and storage CAS do not replace that queue: a source edit after persistence must never be discarded by a later adoption. Cloud sources still require conditional publication, conflict handling, committed-upload recovery, fresh destination verification and atomic index adoption. Local sources still require the normal explicit KDBX export workflow. The original file selected by the user is not a writable file handle.

The initial operation deliberately authenticates and round-trips the complete file. This work runs only during explicit transfer; it adds no hashing, KDF or storage work to Passkey login/autofill paths. Test fixture timings are not large-vault performance measurements.

All fixtures use synthetic data. No user browser profile/account, Android source/build/device, real OneDrive account or real WebDAV account was used.

- Full suite: **3,445 tests / 287 files passed**, including 47 new source-removal cases. - Production build, project/interop types, strict E2E/harness types and the **218-command security audit** passed. The production `dist` is updated; version remains **0.1.37**. Existing large-chunk build warnings remain; this block does not claim to resolve bundle size or chooser latency.

Each case aborts a real file+receipt transaction, verifies complete rollback, loses a later successful response, closes/reopens Edge and recovers with no live source session. Exactly three original project/Passkey entries are in the recycle bin and one untouched entry remains. Original-key signature, zero counter, native fields, current/history attachment bytes and the unchanged base file pass. Restoring the three entries and replaying the old request leaves all four active.
