# MDBX sources to Bitwarden — 0.1.37 development

## Implemented behavior

The existing Bitwarden batch destination now accepts eligible native MDBX sources. The reader authenticates the open native vault ID and revision, checks the selected object's exact remote ID, collection and head commit, and compares its decoded content with the current extension index. It reconstructs the native payload without its original-field merge and accounts for every native content field before the separate Bitwarden round trip. Unknown fields, conflicting aliases, unsupported relationships and incompatible Passkey policies stop the entire linked component before writing. Native routing is replaced by the destination identity; credential IDs, private-key bytes and counters are preserved.

Attachments are read through the production native service. The complete catalog and bytes are bound to the prepared copy; catalogs, object content, folder hierarchy and native revision are checked again after reads. The normal encrypted Bitwarden batch journal retains recovery intent and file bytes before HTTP writes. Preview execution rereads the native source and checks its fingerprint. Resuming an already staged copy uses that reviewed snapshot, retaining the original source.

MDBX password-project membership is checked across all native folders, including the internal root. The bounded scan compares member IDs, folders and head commits with the indexed selection, detecting unsynchronized, missing, moved or changed members. Duplicate/ambiguous pages and unfamiliar membership formats fail closed. A weak cache scoped to one preview or execution state and authenticated native revision retains only identity metadata, avoiding a whole-vault rescan per project member. A new execution state or changed revision requires a new catalog. Ungrouped records do not trigger this scan. This work runs during explicit batch operations, not list navigation or autofill.

The root-collection catalog must include the internal root UUID to prove that an item belongs to the unnamed root. Excluding it caused otherwise valid copies to report an incomplete path; the production reader now includes and validates it. Missing root evidence still blocks preservation of the hierarchy.

## MDBX Passkey metadata

The codec now reads and writes `is_discoverable`, `is_user_verification_required`, `created_at`, `last_used_at`, `use_count` and `icon_url`. These fields are consumed by the current Android `MdbxViewModel` source inspected read-only. Unknown or malformed booleans, dates, counters or icon shapes decode as opaque records with the original native payload retained. Invalid outgoing metadata is refused. Unrelated edits preserve original absent/null/default and unknown fields; explicit clearing of optional usage/icon metadata is represented without altering credential or key material.

The Bitwarden portable route still follows its narrower native schema: UV=false, explicit nondefault backup flags, custom transport/icon data and other unrepresentable fields are refused as documented in [Local records to Bitwarden](bitwarden-local-portable-319.md). Native created/usage timestamps are not a portable audit history; Bitwarden target creation/usage timestamps follow destination behavior. The MDBX commit timeline is not exported as Bitwarden password history. Existing source timelines are retained because this workflow only copies. Legacy password groups without the compatible credential metadata marker remain blocked rather than silently losing grouping.

- Three installed Edge scenarios passed: the final MDBX/fresh-client attachment case (22.4s), the existing local-source registration/copy/restart/fresh-client case (21.7s), and the native Bitwarden graph/folder recovery regression with two full restarts (10.5s). Project types, strict E2E types, production build and the 217-command output security audit passed. Original `dist` is updated.

Evidence remains local under `.artifacts/mdbx-bitwarden-source-*20261012*` and `.artifacts/mdbx-bitwarden-native-regression-edge-20261012*`. ## Remaining scope

This block does not establish complete Android parity. Subsequent [KeePass source integration](bitwarden-keepass-source-319.md) provides native validation for eligible KDBX records and adds bidirectional MDBX projection checks for cleared optional fields. Legacy WebDAV native-source conversion into Bitwarden, the remaining field/backend matrix, durable foreign-source moves, actual direct OneDrive/current Android/F-Droid/system Credential Manager acceptance, nearby transport and per-recipient Passkey consent remain open. The historical fixture is not evidence of current Android runtime acceptance. No Android edits/builds/device actions, real accounts, user Chrome access, release, push or tag are included.
