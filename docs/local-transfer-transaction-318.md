# Local transfer transaction — 2026-10-11

The encrypted local-vault transaction is implemented and tested. The transfer dialog still exposes MDBX destinations only: local target selection, authenticated backend resource collection, local attachment viewing/editing and outbound attachment bridging are the next integration block. This document does not claim a completed local-destination feature or full Android parity.

## Implementation

- `core/local-transfer.ts` prepares a complete selection using the existing password-project, linked-note, SSO and bound-OTP dependency graph. Copies receive deterministic item/project/attachment IDs; project credential metadata is rebased while password IDs, history, custom fields, raw Steam JSON and unknown item fields remain intact. Logical links point to the copied items; Android numeric binding IDs are never transplanted as working links.
- Local folder moves retain item IDs and require confirmation. Existing category identities are supported; preserved external folders receive source-scoped identities, so equal folder IDs/names in different databases remain separate. Missing folder information, ambiguous links, unreadable image references and incomplete groups fail without writing a partial selection.
- Local attachments and archival source envelopes are stored with their owner inside the encrypted vault. Attachment ownership, duplicate IDs, declared length and SHA-256 are checked, including empty files. The transaction currently accepts at most 200 related items, 512 attachments per item and 16 MiB of attachment plaintext per selection. It refuses capacity failures; it does not drop files. Archives are separate from live `sourceRecords` and cannot accidentally restore a remote provider binding.
- `SecureVaultService.prepareLocalTransfer` and `commitLocalTransfer` are background-only methods. Prepared batches contain secrets and are not runtime DTOs. Commit derives the intended result again under the existing exclusive write lock and compares source/dependency/folder/attachment snapshots. It writes items, files, source archives, folder metadata and the receipt in one encrypted envelope. No remote mutation is queued by this transaction.
- A committed operation replays from its encrypted receipt. Later edits/deletions on either side do not get overwritten, and a deleted copy is not recreated. Corrupt receipts and reuse of an operation ID for different content fail. Receipts are bounded and are not silently evicted.
- Uncommitted preparation is tied to its unlock session; expiry or replacement before the storage commit rejects it. A committed receipt can be recognized after a later unlock. Remote-source deletion is not performed by the local transaction; foreign moves still require the separate durable source-deletion workflow.
- Passkey copies validate key usability, identity, counters and backup flags. They retain credential ID, PKCS8, public key, counters/high-water mark and registration flags verbatim, while changing only the storage binding to local. A duplicate local credential is rejected. Existing local folder moves do not modify the key or counter policy.

## Additional persistence fixes

`encryptVaultState` now checks the UTF-8 serialized payload plus the 16-byte GCM tag against the reader's 64 MiB limit before encrypting/writing. Previously, the writer could produce an envelope that the reader would subsequently refuse. Encoded plaintext still clears on success or failure. Canonical transfer-snapshot hashing now clears its encoded secret buffer in `finally` as well.

The production security audit initially rejected an unnecessarily imported UI capability property named `localStorageOnly`. The background planner now imports the exact key/identity/flag/counter validators it needs; the audit itself was not weakened and no Web Storage was introduced.

## Verification and limits

- 12 regression files / 187 tests passed, covering secure-vault persistence, existing MDBX transfer/adoption, dependency expansion, attachments, folder/project links, crypto and snapshot identities. Five additional local cases then passed in the final 30-test local suite. The final key-policy run passed 40 tests across two files, overlapping the local suite.
- Synthetic EC Passkeys with counters 0 and 9 were copied, persisted to an actual encrypted disk file, reopened through a new service instance and independently signed/verified with WebCrypto. Original key/ID/counter/flag values remained identical. This is storage/cryptographic verification, not a new real-site, Android Credential Manager or real Bitwarden-account acceptance claim.
- Actual installed Edge 155.0.4283.45, isolated test profile: production service and `IndexedDbVaultStorage` bundled into a synthetic-origin test harness. Aborted the real IndexedDB transaction after `put` succeeded; verified byte-identical original envelope. Then committed a two-member project and deliberately lost its response. Closed/restarted Edge, unlocked the persisted vault, edited/deleted a target and retried; exactly four total items and one receipt remained, with original source/history preserved and no resurrection. One scenario passed in 11.7 seconds. The harness is not shipped in `dist` and is not a product runtime endpoint.
- Production build passed (project/interop TypeScript, 236 icon references, all three extension pages). The new Playwright file passed standalone TypeScript checking. Built-output security audit passed all 212 runtime commands; the command surface is unchanged. Original `dist` was rebuilt at version 0.1.37.
- Initial failures were fixture mistakes (constructor argument position, missing required Passkey metadata, property-absence assertions and the harness's missing production Node-crypto fallback alias); retained logs distinguish those failures from successful runs.
